# Operator guide

Overview shows discovered subsystem masters, online inventory counts, current critical threshold counts, latest synchronized fast-category source-to-GUI processing latency and subsystem cards. Click a card to inspect its SOMs; click Inspect to see categories, values, freshness, clocks and trends. Global search matches SOM IDs/IPs on inventory pages and parameter names/IDs on SOM detail. Parameter tables sort by stable identifier; fault and command archives are newest-first. Charts combine a bounded historical query with current live data.

Fault console separates current BIT violations from the event archive, with severity, event-state, time-order and text filters. Historical ACTIVE transitions are labeled RAISED. Click a source to navigate to the responsible parameter. ACTIVE and CLEARED rows are historical event transitions, not a separate live alarm lifecycle database. Current critical parameter count comes from current measurements. Acknowledgment records operator awareness and never clears the physical condition. Historical gap banners identify unarchived source loss and boot discontinuities; they cannot restore lost data.

Operations targets a stable SOM and current boot session. Start/stop/restart are operator actions; admin is required for approval, reset, PL/software changes, transfer and configuration. Disruptive operations open a confirmation dialog. Reset/PL/update return UNKNOWN until CPU snapshot evidence reconciles them; a disconnection is never success. Failed reconciliation remains UNKNOWN with an explanation. Do not blindly retry uncertain disruptive operations with a new command ID.

For active-master maintenance, first choose an eligible successor and transfer leadership. Wait for Overview to show the CPU connected to that successor. Only then request maintenance on the previous master. The CPU and agent reject disruptive maintenance against the current master. Failed returning SOMs are QUARANTINED. Inspect their diagnostics and approve the current boot before starting processing or allowing election eligibility. Approval for an old boot is invalid.

Configuration edits the selected SOM's parameter policy JSON: IDs/types/categories, collection/publication intervals, thresholds, deadbands and retention. Validate and apply records the policy in the archive. Collection and publication are distinct from the 100 ms GUI batch interval; a 5-second source sample cannot meet sub-second change visibility. Editing voting inventory/endpoints or roles requires deployment configuration and coordinated restart as documented in the configuration reference.

Simulation controls inject temperature, master failure, return/quarantine, overflow and PTP degradation through provider/link behavior. They are absent in hardware mode. The sidebar indicates CPU connection. The browser retries disconnects and refreshes a snapshot. Stale data and CPU archive errors must be resolved before interpreting old values as current. Authentication uses a session-stored bearer token for production; close the session or clear browser session storage to sign out. One active operator is the initial concurrency target.

If all SOMs boot quarantined and no master is present, approve one inspected candidate through Operations. The CPU's narrowly scoped recovery path sends boot-bound approval directly; processing remains stopped. Once a quorum grants that candidate leadership, approve the remaining healthy SOMs normally. A minority still cannot execute operational commands.
