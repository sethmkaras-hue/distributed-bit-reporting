# Architecture and initial contracts

BITMesh is a Python 3.12 asyncio SOM agent, a FastAPI/SQLAlchemy CPU archive and a React/TypeScript operations console. One agent process runs per SOM in production. The local simulator creates separate gRPC listeners and agent objects with the exact same peer, telemetry, event, archive acknowledgment and command paths. Simulation changes provider inputs and link state; it does not write directly into the CPU archive. CPU connections originate toward inventory addresses. PostgreSQL is the production archive; SQLite WAL with FULL synchronization is the local development archive. No CPU HA, image provisioning or rollback is implemented.

## Communication

`protocol/mesh.proto` defines versioned gRPC operations. The payload is UTF-8 JSON validated against shared Pydantic models; BIT values retain explicit tagged types. This permits category metadata to evolve without a new wire field per parameter. Unknown schema versions are rejected. Peer exchanges carry membership, leadership grants and health. CPU read-only Identity discovery checks a quorum certificate and challenges grantors before opening separate Live and Events server streams. Snapshot and Replay reconcile state independently. Acknowledge relays durable CPU archive receipt to the source. Command and Configure require current fenced authority. Production gRPC uses mutual TLS; development insecure transport binds loopback only. REST and WebSocket are browser-to-CPU only, with configurable bearer authentication and roles. Remote production access requires TLS termination.

## Leadership and safety

The voting set is the fixed configured subsystem inventory (4–16 nodes). A majority of that fixed set must grant one candidate a monotonic-clock lease. A voter cannot grant a different candidate until its previous grant expires; renewals are granted only to the current candidate and boot identity. Candidates choose the lowest eligible reachable numeric IP when no valid incumbent exists. Live incumbents remain non-preemptive. Each grant is bound to candidate boot UUID and a unique leadership-tenure generation UUID. A SOM that loses authority mints a fresh generation before candidacy again, even in the same boot; snapshot epoch changes force CPU rediscovery. Authority expires earlier at the candidate than at voters, accounting for bounded request delay. Before a disruptive command, the master obtains a fresh quorum validation; the target independently verifies live grants before executing and rechecks after acquiring its command lock. Challenges return remaining validity, subtract the entire challenge round-trip and require a further 500 ms execution margin. Boolean grant validity sampled near expiry cannot authorize new operations. No majority means no authoritative commands. Membership reconfiguration requires a coordinated restart, not a live change to the voting denominator.

Safety assumes non-Byzantine authenticated peers, monotonic clock rate error below 1%, configured request timeout 100–500 ms (250 ms default) and a 500 ms lease safety margin. Production suspend/resume and clock behavior require platform validation. A rebooted voter starts with a full lease-duration voting blackout so volatile grant loss cannot produce overlapping leases. A rebooted or explicitly failed SOM is quarantined. An already connected agent returning from total peer isolation or a scheduling hang also enters quarantine before handling requests; one peer alone cannot quarantine another node. Reintegration approval is bound to current boot identity. A process launched on a real SOM defaults to quarantine; only an explicit simulator bootstrap enables initial READY. The minority may continue BIT collection but sacrifices command availability. This is a lease protocol, not durable consensus: inventory must remain fixed, identities exclusive, and transport identities trusted. Read the hardware guide before deployment.

## Data and buffers

Parameter definitions carry stable parameter and SOM IDs, tagged type, units, thresholds, category, collection/publication intervals, deadband and retention. Measurements include source wall time, monotonic scheduling age and timestamp quality. Source/master/CPU/browser times support measured pipeline latency. Only monotonic clocks drive leases, freshness and scheduling.

Events are keyed by (som_id, boot_id, sequence). Each source owns a bounded RAM journal, byte-accounted current/history cache and bounded transport queues under a configurable 16–64 MiB budget. Journals take priority over ordinary history. Overwrite records sequence gaps, including unacknowledged losses. Reboot destroys RAM history; boot changes are archived as explicit loss-of-continuity events. CPU transactions deduplicate events and commit before acknowledgment. Replays run on a separate bounded stream. CPU retention jobs apply category policy; audit, approvals and delivery gaps remain separately recorded.

## Commands and lifecycle

Lifecycle (BOOTING, QUARANTINED, READY, ACTIVE, MAINTENANCE, FAILED), link (CONNECTED, DISCONNECTED) and role (FOLLOWER, MASTER) are separate fields. Commands use stable request IDs, operator and boot identity, deadlines, validation and an audit trail. Target agents cache bounded terminal results, while the CPU persists command state. Retrying a disruptive command after uncertain delivery requires reconciliation, not blind redispatch. Reset and PL programming remain UNKNOWN until a status reconciliation demonstrates the requested boot/artifact. PL/software completion additionally requires a matching current-boot operation receipt emitted after the simulated outage completes; stale READY snapshots cannot establish completion. The agent independently runs PS sampling during simulated PL network outages. PL values become unavailable; RAM replay follows reconnect. Planned master maintenance transfers authority and verifies CPU connectivity first.

## Risks and scope of evidence

Real hardware adapters are intentionally unsupported until Kria interfaces are specified. PTP accuracy, PL Ethernet recovery, power/reset interfaces, signed artifact verification and application process supervision need hardware integration. Simulation is not certification. Performance gates measure fast categories only; slow sample policies cannot promise sub-second visibility. SQLite validates development behavior, not PostgreSQL throughput or target SOM RSS. Runtime process and Python overhead are outside the byte-accounted BIT buffer budget and must be measured on target.

## All-quarantined bootstrap

If every SOM starts quarantined, no operational master exists. The CPU exposes one narrow recovery exception: an authenticated admin may send a boot-scoped approval directly to a discovered SOM using its CPU mTLS identity. The target accepts this exception only for `approve`, only from certificate CN `cpu`, and only for its own current boot. It does not authorize start, reset, PL or other operational commands without a quorum lease. Quarantined peers may vote but cannot be candidates, so approving one healthy candidate can establish a majority-backed master. This recovery exception also works after complete subsystem reboot; no persistent SOM grants or history are presumed.

CPU command and reconciliation deadlines use monotonic time. UTC request age is converted once at ingress; persisted deadlines are reconstructed once after CPU restart. Last-seen boot identities are loaded from the persistent connectivity archive, so a new CPU process can report a reboot/history discontinuity that occurred while offline. Old boot-session measurements are rejected after reconciliation.
